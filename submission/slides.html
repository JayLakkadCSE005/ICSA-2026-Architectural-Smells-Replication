RESEARCH MOTIVATION

The Architectural Technical Debt Dilemma

1. Architectural Smells

  • Code smells are class-level; Architectural Smells span multiple packages and modules.
  • Smells like Cyclic Dependencies and God Components degrade maintainability and agility.
  • They accumulate silently as technical debt during rapid software evolution.

2. The Tri-Metric Trade-off

  • RQ1 Quality: Do structural and modularity metrics genuinely improve?

  • RQ3 Performance: Does decoupling improve throughput or introduce indirection overhead?

SMELL TAXONOMY

Architectural Smells & Refactoring Solutions

Cyclic Dependency (CD)

  • Flaw: 2+ packages depend on each other directly/indirectly, forming a cycle.
  • Impact: Hinders modular testing and independent package deployment.
  • Solution: Apply Dependency Inversion (DIP); extract shared types to dedicated package.
  • Case: Jackrabbit: Moved MalformedPathException to new exception package.

Cyclic Hierarchy (CH)

  • Flaw: A parent class directly depends on one of its own subclasses.
  • Impact: Inverted inheritance, violates polymorphic design.
  • Solution: Consolidate duplicate subclass logic into parent class.
  • Case: ActiveMQ: Merged ManagedTransportConnector into TransportConnector.

Unstable Dependency (UD)

  • Flaw: Stable components depend on volatile, less stable components.
  • Impact: Violates the Stable Dependencies Principle (SDP).
  • Solution: Relocate volatile dependencies into dedicated helper utility classes.
  • Case: Jackrabbit: Extracted SecuritySessionImplManager into util.

God Component & Feature Concentration

  • Flaw: Monolithic component handling excessive disparate duties.
  • Impact: Single point of failure, severe architectural bottleneck.
  • Solution: Decompose along bounded contexts into autonomous modules.
  • Case: Evaluated in the noModularity version across all systems.

RQ1 DEEP DIVE

Package Granularity vs. Class-Level Invariance

Package Level (Macro Architecture)

  • Massive Improvements Across Every Metric:
    • Cyclomatic complexity drops by up to -66%.
    • Package-level coupling drops by up to -44%.
    • Inter-module fan-out cut by half.
  • Why? Modularity refactoring redistributes responsibilities across cohesive packages and dismantles God Components.

Class Level (Micro Implementation — Invariant)

  • Metrics Show Almost Zero Change (|Δ| < 0.1):
    • Class Cyclomatic (WMC): Δ = 0.00 to -0.04
    • Class Coupling (CBO): Δ = -0.01 to +0.02
    • Class Cohesion (LCOM): Δ = -0.00 to -0.06
  • Crucial Takeaway: Architectural smell refactoring cleans up system topology without mutating or rewriting localized class algorithms!
RQ2: SECURITY FINDINGS

Negligible Impact on Security Vulnerabilities

Empirical Finding

  • Evaluated projects: Apache ActiveMQ, Jackrabbit, Oozie.
  • Tools: SonarQube & SpotBugs static security rules.
  • Metrics: Vulnerabilities, Security Hotspots, Security Technical Debt.
  • Outcome: Removing architectural smells exhibited no statistically significant reduction in security vulnerabilities!

The Abstraction Level Mismatch

  • Architectural Smells (Package Scope):
    Package cycles, inverted inheritance, God Components.
  • Security Vulnerabilities (Statement Scope):
    CWE-89 (SQLi), CWE-502 (Deserialization), unvalidated input, weak cryptography.
  • Architectural Lesson: Moving a class or decoupling a package does not add input sanitization! Dedicated security audits remain essential.

PERFORMANCE CAUSALITY

Why Does Architecture Impact Performance?

1. Garbage Collection

  • Circular dependencies cause cross-generational reference retention.
  • Decoupling allows the JVM Garbage Collector to reclaim objects immediately without long generational pauses.

2. JIT Inlining

  • Cyclic hierarchies force dynamic polymorphic virtual dispatch.
  • Flattening inheritance hierarchies allows the HotSpot JIT compiler to inline methods aggressively, reducing CPU branch stalls.

3. Bounded State

  • Monolithic God Components hoard massive heap state.
  • Modular bounded contexts restrict in-memory caching to short-lived scopes, lowering cloud container RAM requirements.
EMPIRICAL CASE STUDIES

Concrete Refactoring Examples From Study

Cyclic Dependency (CD)

  • System: Apache Jackrabbit
  • Problem: TDI 22 cycle between two core packages.
  • Fix: Created dedicated exception package; relocated MalformedPathException.
  • Outcome: Clean separation of concerns; cyclic dependency eliminated.

Cyclic Hierarchy (CH)

  • System: Apache ActiveMQ
  • Problem: Child class duplicated parent logic across package boundary.
  • Fix: Merged createConnectionManaged() directly into parent TransportConnector.
  • Outcome: Simplified inheritance; eliminated cyclical hierarchy.

Unstable Dependency (UD)

  • System: Apache Jackrabbit
  • Problem: Stable security package depended on unstable modules (TDI 20).
  • Fix: Created SecuritySessionImplManager in dedicated util package.
  • Outcome: Satisfied Stable Dependencies Principle.
PRACTICAL TAKEAWAYS

Recommendations for Software Architects

1. Prioritize Modularity

  • Modularity refactoring (splitting God Components) yields 10x greater technical debt reduction than isolated dependency inversion.
  • Focus architectural sprints on component boundaries first.

2. Cloud Financial ROI

  • Up to -31% memory heap reduction and -11% CPU utilization directly lower cloud container and Kubernetes hosting costs.
  • Architectural refactoring has direct economic operational ROI.

3. Decouple Security

  • Do not conflate architectural hygiene with security hardening.
  • Architectural governance and SAST vulnerability remediation must be managed as separate, parallel engineering pipelines.
